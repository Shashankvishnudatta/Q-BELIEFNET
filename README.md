# Q-Belief Net

Q-Belief Net is a full-stack market-belief intelligence product prototype. It explores how traders, analysts, and builders might inspect market narratives, prototype belief metrics, watchlists, alerts, portfolio views, and AI-assisted market questions from one dashboard.

This is not a production trading system. The current version makes the product foundation honest: market APIs include provenance metadata, runtime mode is explicit, demo data is labeled, secrets remain backend-only, and the belief engine explains how prototype scores are produced.

## Why It Exists

Market tools often show prices without explaining the narratives forming around them. Q-Belief Net prototypes an interface for belief-oriented signals: sentiment, velocity, coherence, fragility, narrative clusters, and assistant-guided exploration. In the current product stage, those analytics are prototype/demo calculations unless live provider paths are explicitly configured.

## Product Modes

- `demo`: generated/mock data only. Best for local demos and interviews.
- `hybrid`: live-capable providers may be attempted; generated fallback is declared in API metadata.
- `live`: provider configuration is required. If required credentials are missing, APIs fail gracefully with structured errors.

Mode is controlled by backend env:

```env
APP_MODE=demo
DATA_MODE=demo
```

## Mock vs Real Data

- Demo/generated: alerts, portfolio/report views, WebSocket stream content, belief graph, and Phase 2 belief-intelligence evidence.
- Live-capable: trending stocks, stock details, and social/market signals through Yahoo/RapidAPI, Reddit, Stocktwits, and YouTube paths when configured.
- Partial/scaffolded: Redis processing, FAISS vector store, spaCy preprocessing, clustering, embedding workers.
- Not implemented: LangChain. Do not claim LangChain unless added later.

Every market endpoint returns:

{
  "data": [],
  "meta": {

## Belief Intelligence Engine

Phase 2 adds an explainable belief engine at `/api/belief`.

Endpoints:

- `GET /api/belief/{symbol}`: full belief snapshot with score, metrics, narratives, evidence, explanation, delta, and provenance.
- `GET /api/belief/{symbol}/history`: deterministic demo history for belief score, velocity, coherence, and fragility.
- `GET /api/belief/trending`: assets ranked by belief score and velocity.
- `GET /api/providers/status`: provider health and evidence-cache status.

The engine does not predict prices and does not issue trading recommendations. It analyzes interpretive market-belief signals.

### Belief Score Formula

Belief score is a 0-100 prototype signal combining:

- attention: volume and intensity of available evidence,
- sentiment: weighted positive/negative tone,
- momentum: recent change in belief formation,
- source agreement: alignment across source categories,
- inverse fragility: lower instability improves the score.

In plain English:

```text
belief score = attention + sentiment + momentum + source agreement + inverse fragility
```

with weights applied in `backend/app/services/belief_engine.py`.

### Metric Definitions

- Attention: how much belief evidence exists and how intense it is.
- Velocity: how quickly belief intensity is changing.
- Coherence: whether narratives point in similar directions.
- Fragility: how unstable the belief is because of sparse evidence, volatility, or source concentration.
- Source agreement: how aligned evidence categories are.

### Narrative Clustering

Narratives are grouped with lightweight keyword rules, not heavy ML. Current groups include earnings, product/news, analyst ratings, macro/rates, valuation, regulation, social hype, risk/fear, and technical momentum.

### Evidence Model

Demo evidence is generated by `internal-demo-generator` and every evidence item is labeled as synthetic demo evidence for product exploration. It should not be treated as live news or live social data.

## Evidence Provider Layer

Phase 3 adds a transparent evidence pipeline:

```text
Providers -> Evidence Pipeline -> Belief Engine -> API/WebSocket -> Frontend Panels/LLM Context
```

Current providers:

- `internal-demo-generator`: deterministic synthetic evidence for demo mode and explicit fallback.
- `market-data-provider`: live-capable wrapper around the existing market-data path. It requires backend provider credentials and returns structured unavailable status when not configured.

Mode behavior:

- `demo`: generated evidence only.
- `hybrid`: live-capable providers first, demo fallback with visible warning.
- `live`: live providers only unless `ALLOW_LIVE_MODE_DEMO_FALLBACK=true`.

Evidence bundles include provider results, source mix, freshness summary, per-item provenance, and warnings.

## Freshness And Caching

The backend uses a lightweight in-memory TTL cache for provider results:

```env
ENABLE_EVIDENCE_CACHE=true
EVIDENCE_CACHE_TTL_SECONDS=300
ALLOW_LIVE_MODE_DEMO_FALLBACK=false
ALLOW_STALE_CACHE_ON_PROVIDER_FAILURE=true
STALE_CACHE_MAX_AGE_SECONDS=1800
```

Source mix and freshness are returned with belief snapshots and shown in the stock detail view.

## Provider Observability And Reliability

Phase 4 adds provider runtime metrics and lightweight reliability controls:

```env
PROVIDER_TIMEOUT_SECONDS=8
PROVIDER_RETRY_COUNT=1
PROVIDER_CIRCUIT_FAILURE_THRESHOLD=3
PROVIDER_CIRCUIT_RESET_SECONDS=120
```

Provider status now includes success/failure counts, consecutive failures, average and last latency, circuit state, last result source, result count, fallback usage, and redacted last error.

## Background Refresh Pipeline

Background refresh is optional and disabled by default:

```env
ENABLE_BACKGROUND_REFRESH=false
BACKGROUND_REFRESH_INTERVAL_SECONDS=60
BACKGROUND_REFRESH_SYMBOLS=AAPL,TSLA,NVDA,MSFT,AMZN
```

Flow:

```text
Provider Registry -> Reliability Wrapper -> Evidence Pipeline -> Cache -> Belief Engine -> API/WebSocket -> Frontend Observability Panels
```

Endpoints:

- `GET /api/ingestion/status`: scheduler state, recent runs, cache summary, provider health summary.
- `POST /api/ingestion/refresh`: manually refresh up to 10 validated symbols. This is unauthenticated only for local prototype use and needs auth before production.

## Durable Local Persistence

Phase 5 adds SQLite-backed local persistence so operational state can survive backend restarts:

```env
ENABLE_PERSISTENCE=true
DATABASE_URL=sqlite:///backend/data/qbeliefnet.db
PERSISTENCE_MODE=sqlite
MAX_SNAPSHOTS_PER_SYMBOL=100
ENABLE_MANUAL_REFRESH=true
MANUAL_REFRESH_TOKEN=
REQUIRE_MANUAL_REFRESH_TOKEN=false
MAX_MANUAL_REFRESH_SYMBOLS=10
```

SQLite is the default local persistence mode for prototype use. Postgres or a managed database is recommended before multi-user production deployment.

Persisted stores:

- belief snapshots and snapshot history,
- ingestion run history,
- provider health events,
- cache metadata,
- local workspace state: watchlist, tracking portfolio, belief alert rules,
- operation audit log.

Manual refresh has a local safety guard. In demo/local mode it may run without a token when `REQUIRE_MANUAL_REFRESH_TOKEN=false`. When token protection is enabled, send `X-QBN-Admin-Token`; the token is never returned by status endpoints.

Workspace endpoints:

- `GET /api/watchlist`
- `POST /api/watchlist`
- `DELETE /api/watchlist/{symbol}`
- `GET /api/portfolio`
- `POST /api/portfolio`

## LLM Assistant Flow

The frontend sends questions to `/api/llm`. The backend owns `HF_API_KEY` and `HF_MODEL_ID`. If the key is missing, the backend returns a local belief-aware fallback answer using the belief snapshot context. If a key is configured, the backend prompt instructs the model to explain belief signals and avoid financial advice.

Assistant answers now mention evidence source context, such as live/cached/synthetic counts and freshness, when ticker context is available.

## Security Notes

- Never commit `.env`, `.env.frontend`, or `backend/.env`.
- Never expose Hugging Face or provider keys through `VITE_*`.
- A Hugging Face-style token existed in Git history. Rotate it immediately and purge history before public sharing.
- Use BFG Repo-Cleaner or `git filter-repo`; force-push only after collaborators are informed.

## Known Limitations

- FastAPI still uses `on_event`; migrate to lifespan in a later phase.
- Frontend interaction tests are not yet added.
- CI is not yet configured.
- Live provider quality depends on real credentials and provider reliability.
- Belief analytics are prototype calculations, not investment advice.
- Belief evidence is still synthetic in demo mode. Hybrid/live evidence depends on configured providers.
- Current live-capable market evidence is basic market-derived context, not verified news/social truth.
